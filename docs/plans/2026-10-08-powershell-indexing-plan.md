# Offline PowerShell Indexing

Date: 2026-10-08

Status: planned.

Uses the profile contract in [plan 1](2026-10-08-project-discovery-capability-profile-plan.md) and [capability routing](2026-10-08-capability-aware-tool-routing-plan.md). Parser feasibility can be investigated independently.

## Goal And Recommendation

Add a dedicated .NET `tools/PowerShellIndexer` using PowerShell's native parser/AST APIs. Start with offline source analysis for checked-in `.ps1`, `.psm1`, and literal module-manifest metadata in `.psd1`.

Prefer `System.Management.Automation` for parser-only use, subject to a .NET 10/package compatibility and packaging spike. Microsoft documents this package as suitable for parser/AST static analysis, and `Parser.ParseFile` returns AST, tokens, and parse errors. Pin the tested runtime package and record its language/version fingerprint. Do not choose a version from examples in documentation. Sources: [PowerShell package guidance](https://devblogs.microsoft.com/powershell/depending-on-the-right-powershell-nuget-package-in-your-net-project/), [Parser.ParseFile API](https://learn.microsoft.com/en-us/dotnet/api/system.management.automation.language.parser.parsefile?view=powershellsdk-7.4.0).

Keep dependencies inside the worker rather than Core or the MCP server. No requirement for an installed `pwsh`/Windows PowerShell executable should be introduced unless the compatibility spike proves a packaged-parser approach unavailable and the tradeoff is explicitly revisited.

## MVP Facts

| Fact | Semantics |
|---|---|
| Script/module file | Stable project-relative file identity and parser status |
| Function/filter definition | Name, lexical scope, parameters, extent, and bounded source snippet |
| Script entry body | Top-level statements represented without calling the whole file a class |
| Static command occurrence | Raw command name, invocation kind, source span, and owning body |
| Local callable dependency | Calls edge only when supported binding establishes a unique target |
| Static script/dot-source reference | File dependency with resolution evidence; dot-source semantics remain distinct |
| Static module reference | Literal `Import-Module`, `using module`, and `#requires -Modules` facts |
| Literal manifest metadata | Static known fields and exported-name declarations; no evaluation |
| Parse diagnostic | Exact parser message/code/span and analysis completeness |

MVP functions, filters, and script bodies come first. Classes/enums, detailed variable data flow, embedded SQL, pipeline value-flow, binary-module inspection, runtime alias tables, and semantic Pester shields are deferred.

## Offline Resolution And Honest Limits

PowerShell command resolution depends on scopes and command precedence; dot-sourcing affects the receiving scope. Use explicit static evidence rather than matching global names. Sources: [command precedence](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_command_precedence), [script scope and dot-sourcing](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_scripts?view=powershell-7.6).

- Preserve case-insensitive PowerShell command names while respecting filesystem path case.
- Resolve lexical local definitions only where visibility and shadowing rules are supported.
- Same-named functions in unrelated files do not become candidates solely by name.
- Imported module, alias, conditional declaration, and redefinition ambiguity must reduce confidence or remain unresolved.
- Statically supported paths may include literal paths and a narrowly specified `$PSScriptRoot` composition; arbitrary expressions remain indeterminate.
- A literal relative path depends on context. Do not universally resolve it relative to the source file when runtime working directory semantics apply.
- Dynamic `& $command`, splatting-dependent resolution, `Invoke-Expression`, computed imports/exports, and indirect scriptblocks remain occurrences with limitations rather than invented call targets.
- Cmdlets/native commands are external/unindexed unless an explicit supported repository declaration establishes a local target.
- Parse `.psd1` AST literals; never call `Import-PowerShellDataFile` or evaluate expressions to discover metadata.
- Module export lists restrict supported exported symbol visibility; wildcard/computed exports require stated limits.
- No runspace, pipeline invocation, dot-sourcing, module loading, profile loading, build hook, or source script execution for analysis.

Record binding outcomes using the existing relationship-health vocabulary where applicable: resolved, unresolved local, indeterminate, and external/unindexed. Index source facts rather than descriptions generated by an LLM.

## Identity, Publication, And Incremental Behavior

Use stable IDs from project, repository-relative path, lexical scope, symbol kind, and name. Handle duplicate declarations deterministically without using source line as the sole identity. Cross-file scope and changed exported definitions may require re-binding unchanged consumers.

Evaluate existing graph node/edge kinds before adding any public enum. Reuse a kind only when generic query assumptions remain true; preserve PowerShell-specific invocation evidence in metadata or a minimal new relationship where necessary.

Publication must be analyzer-owned and generation-safe:

1. Parse and bind a bounded analysis scope offline.
2. Publish successful file facts atomically where possible; never clear the previous graph before parsing.
3. Replace only PowerShell-owned nodes/edges; preserve manual/other-language facts.
4. Mark failed files stale and prevent old facts from being advertised as fresh capability evidence.
5. Remove deleted-file ownership safely, including edges owned by callers in unchanged files.
6. Do not advance the successful cache on transport/publication failure; support replay and cancellation.
7. Invalidate binding when source inventory, imports/exports, settings, or parser fingerprint changes.

The transactional SQL publication is an existing pattern to inspect, not an interface to reuse blindly. Adapt existing ingestion only if it proves the required ownership/failure guarantees; otherwise add a small parser-independent publication contract and Infrastructure implementation.

## Integration Surfaces

- Proposed `tools/PowerShellIndexer/` and `tests/CodeMeridian.PowerShellIndexer.Tests/`: parser adapter, extraction, conservative binder, mapping, and fixtures.
- `tools/Indexer/Cli/IndexCommandHandler.cs`, `IndexExecutionPlanBuilder.cs`, `Commands/RootCommandFactory.cs`: dispatch, dry run, watch, exclusions, deletion inventory, and exit semantics.
- `src/Tooling/Discovery/ProjectDiscoveryService.cs`: reuse file detection and profile scope support.
- Tooling configuration models/service, `meridian.schema.json`, templates: proposed `indexing.powershell.enabled` and `--skip-powershell`; default opt-in for initial release.
- Incremental cache, SDK/API publication, Core contracts, Infrastructure storage: source ownership and delivery semantics.
- CLI packaging and CI: bundled worker/parser dependencies and clean Windows/Linux installations.
- Application/query tool catalog: advertise symbol/impact capabilities only after query-conformance tests pass.
- Proposed `tools/PowerShellIndexer/supports.md`: syntax, binding, parser version, platform support, and unsupported constructs.

Graph feature matches for PowerShell were generic snippets/document indexing. No existing PowerShell implementation was established; those matches are not a reason to edit snippet services.

## Phases And Gates

1. Compatibility spike: native parser package on .NET 10, isolated dependency loading, clean Windows/Linux packaging, syntax/encoding fixtures; select and pin version.
2. Extract definitions, body identities, occurrences, parameters, literals, and parse diagnostics; include non-execution tests.
3. Implement conservative local/static-file binding with provenance and scope-reanalysis tests.
4. Implement owned publication, failure recovery, deletion, cache behavior, CLI/config/profile integration.
5. Validate existing generic query compatibility; activate only proven capabilities.
6. Ship Windows/Linux CI, package-install smoke tests, supports documentation, and read-only sample acceptance.

First usable release comprises phases 1-6 with limited bindings. Pester executable-case extraction/test shields and PowerShell classes are separate follow-ups; file-role detection alone does not prove test protection.

## Verification And Acceptance

- Parser fixtures: functions, filters, advanced parameters, nested definitions, top-level commands, pipelines, comments/help, here-strings, modules/manifests, syntax errors, UTF-8/BOM and declared encoding policy.
- Binding fixtures: command case, lexical scope, same-name collisions, local/remote modules, literal versus dynamic paths, import/export visibility, redefinitions, and indeterminate invocation.
- Non-execution fixture contains observable side-effect code; indexing must not execute it, load profiles, or import modules.
- Contract fixtures validate stable IDs, source extents, cancellation, diagnostics, unsupported evidence, and no false external-to-local links.
- Publication tests cover replay, partial failure, manual-edge preservation, unchanged consumers after declaration changes, deletion, and transport retry.
- CLI fixtures cover opt-in/skip, full/incremental/watch/dry run, exclusion policy, spaces/non-ASCII paths, and settings precedence.
- Query fixtures cover exact resolution, minimal context, impact/connection, snippets, project scoping, and callable target semantics.
- Fresh isolated Neo4j verifies publication/query behavior. A packaged CLI smoke test runs on Windows and Linux without relying on globally installed PowerShell.
- Explicit read-only acceptance may index `ava-sporelight/scripts/` under a separate temporary project/cache, with user-selected scope; never run its publishing scripts or alter the repository.
- Unit tests use checked-in synthetic scripts rather than an absolute path to another repository.

## Risks And Follow-Ups

PowerShell is dynamic, and native parsing does not guarantee runtime name resolution. Parser version compatibility with Windows PowerShell 5.1 syntax must be documented rather than assumed. Dependency/package footprint, encoding policy, incremental cross-file binding, and legacy generic-query filters are release gates. PSScriptAnalyzer and Pester integration are optional later work and must not become prerequisites for offline parsing.
